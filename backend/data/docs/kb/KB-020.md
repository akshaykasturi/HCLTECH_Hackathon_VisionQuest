# Customer API outages and errors

## Symptoms and scope

The customer API returns errors or is unavailable for some or all users. Causes include dependencies, deployments, capacity and traffic patterns.

This guide covers these known causes:

- Faulty release causing the service to crash on startup (typical signal: `HTTP 503`)
- External dependency timing out without a circuit breaker (typical signal: `upstream timeout`)
- Backend certificate expired (typical signal: `HTTP 502`)
- Autoscaling maximum reached (typical signal: `scale limit reached`)
- Partner exceeding their rate limit (typical signal: `HTTP 429`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to API dashboards, logs and the deployment pipeline. Production changes during an outage need the incident commander's approval. Communicate status through the incident channel.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Faulty release causing the service to crash on startup.** When errors start at a deployment, compare the error start time with the release time in the pipeline.
- **External dependency timing out without a circuit breaker.** If latency rises, read traces to find which dependency call is slow.
- **Backend certificate expired.** When the gateway returns 502, check the gateway log for TLS errors to the backend.
- **Autoscaling maximum reached.** If errors grow with traffic, check instance count against the autoscaling maximum.
- **Partner exceeding their rate limit.** When one customer gets 429s, check their request rate against their plan limit.

## Resolution steps by cause

### Faulty release causing the service to crash on startup

1. Compare the error start time with the release time.
2. Roll back to the previous release with incident commander approval.
3. Confirm the error rate drops.
4. Open a problem record for the faulty release.

### External dependency timing out without a circuit breaker

1. Identify the slow dependency in traces.
2. Enable the documented circuit breaker for the dependency.
3. Contact the provider through the support channel.
4. Confirm latency returns to normal.

### Backend certificate expired

1. Check the gateway log for backend TLS errors.
2. Renew and deploy the backend certificate.
3. Confirm the gateway reaches the backend.
4. Add the certificate to expiry monitoring.

### Autoscaling maximum reached

1. Check instance count against the autoscaling maximum.
2. Raise the autoscaling maximum with incident commander approval.
3. Confirm error rate drops.
4. Review capacity planning with the service owner.

### Partner exceeding their rate limit

1. Check the partner's request rate against the plan limit.
2. Share the rate limit and retry guidance with the partner.
3. Agree a temporary limit change with the account owner if needed.
4. Confirm the partner's errors drop.

## Validation and escalation

Confirm the error rate and latency are back within objectives for at least 30 minutes, and the status page is updated.

Escalate to the on-call incident commander immediately for customer-facing outages affecting more than one region.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
