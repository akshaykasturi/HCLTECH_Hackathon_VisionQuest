# MFA sign-in failures on the SSO Portal

## Symptoms and scope

Users cannot complete multi-factor authentication on the SSO Portal, or are sent back to the MFA prompt after approving it. Impact is usually one user, but a policy or app change can affect many users at once.

This guide covers these known causes:

- Authenticator registration still bound to the retired device (typical signal: `AADSTS50076`)
- Device clock drift makes time-based codes expire before use (typical signal: `invalid verification code`)
- New conditional access policy requires a managed device (typical signal: `AADSTS53000`)
- SMS delivery delays on roaming networks (typical signal: `SMS delivery timeout`)
- Outdated authenticator app version without number matching (typical signal: `unsupported app version`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need the Identity Operations role in the identity admin console and read access to sign-in logs. Verify the caller's identity before changing any authentication method.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Authenticator registration still bound to the retired device.** When sign-ins loop after a device change, list the user's registered MFA methods and check whether the only authenticator entry belongs to the retired handset.
- **Device clock drift makes time-based codes expire before use.** If time-based codes are always rejected, compare the device clock with network time; a drift of more than 30 seconds invalidates every code.
- **New conditional access policy requires a managed device.** When MFA completes but access is still denied, open the sign-in log entry and read which conditional access policy failed and why.
- **SMS delivery delays on roaming networks.** For users relying on SMS codes, check the delivery timestamps in the MFA log and whether the user is on a roaming carrier network.
- **Outdated authenticator app version without number matching.** When push approvals fail after number matching was enabled, check the authenticator app version recorded in the method details against the minimum supported version.

## Resolution steps by cause

### Authenticator registration still bound to the retired device

1. Verify the user's identity through the identity verification workflow.
2. Remove the authenticator registration that belongs to the retired device.
3. Guide the user through registering the authenticator on the new device.
4. Confirm a successful MFA sign-in and revoke the stale sessions.

### Device clock drift makes time-based codes expire before use

1. Confirm the failures in the sign-in log show an invalid verification code.
2. Ask the user to enable automatic date and time on the device.
3. Have the user resync the authenticator time correction setting.
4. Confirm the next code is accepted and record the drift observed.

### New conditional access policy requires a managed device

1. Identify the conditional access policy named in the failed sign-in entry.
2. Confirm with the policy owner whether the user group was meant to be in scope.
3. Enroll the device in management or request a documented policy exception.
4. Confirm sign-in succeeds and note the policy decision in the ticket.

### SMS delivery delays on roaming networks

1. Confirm from the MFA log that SMS codes are delivered after the timeout.
2. Help the user register the authenticator app as the default method.
3. Keep the phone number as a backup method rather than the primary method.
4. Confirm the user can sign in using the authenticator app.

### Outdated authenticator app version without number matching

1. Check the authenticator version recorded for the user's device.
2. Ask the user to update the authenticator app from the official app store.
3. Re-register the push method if the update does not refresh it.
4. Confirm a number-matching approval completes successfully.

## Validation and escalation

Ask the user to sign out of all sessions, sign in again from the affected device and confirm that the sign-in log shows MFA satisfied. Check that no other method was removed by mistake.

Escalate to Identity Operations engineering when several users fail at the same time after a policy change, or when sign-in logs show approvals the user did not make.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
