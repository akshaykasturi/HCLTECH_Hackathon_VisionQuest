# Endpoint detection alerts

## Symptoms and scope

Endpoint detection raises an alert on a device. Alerts range from false positives to active threats. Triage decides whether to contain the device and who must be involved.

This guide covers these known causes:

- Malicious executable run from downloads (typical signal: `high severity detection`)
- Known internal tool matching a behaviour rule (typical signal: `behaviour rule match`)
- Potentially unwanted application installed with free software (typical signal: `PUA detection`)
- Endpoint sensor service stopped after an update (typical signal: `sensor offline`)
- Ransomware behaviour on a device (typical signal: `ransomware behaviour`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need the Security Operations role in the endpoint detection console. Do not connect to a possibly compromised device with privileged credentials. Preserve evidence before cleanup.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Malicious executable run from downloads.** For an active detection, check whether the process is still running and whether the device contacted unknown addresses.
- **Known internal tool matching a behaviour rule.** When an alert names an internal tool, verify the file hash and signer against the software inventory.
- **Potentially unwanted application installed with free software.** For low severity unwanted software, confirm the item and whether it came from a catalogue source.
- **Endpoint sensor service stopped after an update.** If a device stopped reporting, check the sensor service status and last check-in time.
- **Ransomware behaviour on a device.** For encryption behaviour, identify the source device and the shares affected immediately.

## Resolution steps by cause

### Malicious executable run from downloads

1. Isolate the device through endpoint detection.
2. Collect the alert evidence and process tree.
3. Hand the case to the incident response lead.
4. Reimage the device after evidence is preserved.

### Known internal tool matching a behaviour rule

1. Verify the file hash and signer against the software inventory.
2. Record the false positive verdict with evidence.
3. Request a scoped exclusion through the security change process.
4. Confirm no new alerts for the tool.

### Potentially unwanted application installed with free software

1. Confirm the unwanted application and its source.
2. Remove the application through endpoint detection.
3. Remind the user to install software from the catalogue only.
4. Confirm the device scan is clean.

### Endpoint sensor service stopped after an update

1. Check the sensor service status and last check-in.
2. Reinstall the sensor from the device management console.
3. Confirm the device checks in.
4. Review alerts raised since check-in.

### Ransomware behaviour on a device

1. Isolate the source device through endpoint detection.
2. Identify the affected shares.
3. Hand the case to the incident response lead.
4. Restore affected files from backup after containment.

## Validation and escalation

Confirm the alert is resolved with a recorded verdict, and that the device is healthy and released from isolation if it was isolated.

Escalate to the incident response lead for confirmed malicious activity, lateral movement, or any alert on a server or privileged account.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
