# Corporate VPN connection problems

## Symptoms and scope

Users cannot connect to the corporate VPN, or the tunnel connects and then drops. Problems may come from the client, the user's local network, gateway configuration or certificates.

This guide covers these known causes:

- Gateway now requires ciphers that older clients do not offer during rekey (typical signal: `IKE NO_PROPOSAL_CHOSEN`)
- Path MTU too small on the home connection causing packet fragmentation (typical signal: `fragmentation needed`)
- Device certificate used for VPN authentication has expired (typical signal: `certificate expired`)
- VPN address pool exhausted during peak hours (typical signal: `IP pool exhausted`)
- Split tunnelling profile missing on the client so all traffic goes through the tunnel (typical signal: `full tunnel profile`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the VPN gateway logs and the client deployment console. Gateway configuration changes require an approved change record; never share gateway credentials or pre-shared keys in a ticket.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Gateway now requires ciphers that older clients do not offer during rekey.** When tunnels drop at a regular interval, read the gateway log at the time of the drop; a rekey failure with no matching proposal means a cipher mismatch.
- **Path MTU too small on the home connection causing packet fragmentation.** If small requests work but larger transfers stall, test with ping using the do-not-fragment flag at decreasing sizes to find the working packet size.
- **Device certificate used for VPN authentication has expired.** When the VPN fails before the credential prompt, check the device certificate store for the VPN machine certificate and its expiry date.
- **VPN address pool exhausted during peak hours.** When new sessions fail while existing ones work, check address pool usage on each gateway and how many idle sessions are held.
- **Split tunnelling profile missing on the client so all traffic goes through the tunnel.** If only internet-bound traffic is slow on VPN, compare the client's assigned profile with the documented split tunnelling profile.

## Resolution steps by cause

### Gateway now requires ciphers that older clients do not offer during rekey

1. Confirm the rekey failure and the client version in the gateway log.
2. Upgrade the VPN client to the supported version through the deployment console.
3. Ask the user to reconnect after the upgrade.
4. Confirm the session survives past the rekey interval.

### Path MTU too small on the home connection causing packet fragmentation

1. Test the largest unfragmented packet size from the user's device.
2. Apply the documented lower MTU profile to the VPN client.
3. Ask the user to reconnect and reload an internal page.
4. Confirm file transfers complete over the tunnel.

### Device certificate used for VPN authentication has expired

1. Confirm the device VPN certificate has expired.
2. Trigger certificate renewal through the device management console.
3. Ask the user to restart the device while on the office network or a docking connection.
4. Confirm the VPN connects with the renewed certificate.

### VPN address pool exhausted during peak hours

1. Confirm the address pool usage on the gateway is at its limit.
2. Disconnect sessions idle beyond the documented idle timeout.
3. Raise a change to extend the address pool with Network Operations.
4. Confirm new connections receive an address.

### Split tunnelling profile missing on the client so all traffic goes through the tunnel

1. Check which tunnel profile is assigned to the user.
2. Move the user to the documented split tunnelling profile.
3. Ask the user to reconnect the VPN.
4. Confirm collaboration traffic no longer goes through the tunnel.

## Validation and escalation

Ask the user to stay connected for at least 30 minutes while you watch the gateway session, and confirm they can reach an internal application.

Escalate to Network Operations engineering when many users at different locations are affected, or when the gateway shows capacity or certificate errors.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
