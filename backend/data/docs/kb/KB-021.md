# TLS certificate problems on the API gateway

## Symptoms and scope

Clients fail TLS handshakes or see certificate warnings when calling services through the API gateway. Causes include expiry, incomplete chains, name mismatches and protocol settings.

This guide covers these known causes:

- Intermediate certificate missing from the gateway chain (typical signal: `unable to get local issuer certificate`)
- Certificate not renewed before expiry (typical signal: `certificate has expired`)
- New hostname not in the certificate's subject alternative names (typical signal: `hostname mismatch`)
- Client only supports deprecated TLS versions (typical signal: `protocol version`)
- Gateway trust store lacks the partner's new issuing CA (typical signal: `bad certificate`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the gateway configuration and certificate store. Certificate changes need a change record. Never share private keys; use `openssl s_client` style read-only checks for diagnosis.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Intermediate certificate missing from the gateway chain.** When some clients fail after a rotation, check the chain the gateway sends with a read-only TLS check.
- **Certificate not renewed before expiry.** If handshakes fail at a fixed time, check the certificate's expiry date.
- **New hostname not in the certificate's subject alternative names.** When a new name fails, list the subject alternative names on the presented certificate.
- **Client only supports deprecated TLS versions.** If one old client fails after a protocol change, check which TLS versions it offers.
- **Gateway trust store lacks the partner's new issuing CA.** When mutual TLS fails for one partner, compare the partner's client certificate issuer with the gateway trust store.

## Resolution steps by cause

### Intermediate certificate missing from the gateway chain

1. Check the chain the gateway presents.
2. Install the full chain with the intermediate certificate through change control.
3. Retest from an affected client.
4. Confirm handshakes succeed.

### Certificate not renewed before expiry

1. Confirm the certificate expiry date.
2. Issue and install a renewed certificate through change control.
3. Confirm handshakes succeed.
4. Add the certificate to expiry monitoring.

### New hostname not in the certificate's subject alternative names

1. List the subject alternative names on the certificate.
2. Request a certificate that includes the new hostname.
3. Install it through change control.
4. Confirm no warning for the new hostname.

### Client only supports deprecated TLS versions

1. Check the TLS versions the client offers.
2. Ask the partner to upgrade the client to TLS 1.2 or later.
3. Agree a time-limited exception with Security only if required.
4. Confirm the client connects with a supported version.

### Gateway trust store lacks the partner's new issuing CA

1. Compare the client certificate issuer with the trust store.
2. Add the partner's issuing CA to the trust store through change control.
3. Ask the partner to retry.
4. Confirm the partner's calls succeed.

## Validation and escalation

Confirm clients complete the handshake and that a read-only certificate check shows the expected certificate, chain and expiry date.

Escalate to Platform Operations engineering if many services are affected or a certificate authority problem is suspected.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
