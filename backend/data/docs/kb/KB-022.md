# Monitoring and alerting gaps

## Symptoms and scope

Alerts do not fire, notifications do not arrive, dashboards are empty, or too many alerts fire. Causes include notification routes, agents, thresholds and maintenance windows.

This guide covers these known causes:

- Notification route points to an old on-call schedule (typical signal: `route to retired schedule`)
- Monitoring agent stopped after patching (typical signal: `agent heartbeat missing`)
- Maintenance window left open (typical signal: `maintenance active`)
- Threshold set too low without grouping (typical signal: `alert storm`)
- Daily ingestion quota reached (typical signal: `ingestion quota`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the monitoring platform and alert history. Alert rule changes go through the observability change process. Do not silence alerts without an owner's agreement.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Notification route points to an old on-call schedule.** When alerts fire without notifications, check the route and schedule the alert used.
- **Monitoring agent stopped after patching.** If hosts show no data, check the agent heartbeat and service status.
- **Maintenance window left open.** When a service is silent, check for active maintenance windows on it.
- **Threshold set too low without grouping.** When alerts flood, check recent threshold changes and alert grouping.
- **Daily ingestion quota reached.** If logs stop arriving, check ingestion volume against the daily quota.

## Resolution steps by cause

### Notification route points to an old on-call schedule

1. Check the route and schedule on the fired alert.
2. Update the route to the current on-call schedule.
3. Send a test alert.
4. Confirm the on-call engineer receives the page.

### Monitoring agent stopped after patching

1. Check the agent heartbeat for the hosts.
2. Restart the monitoring agent service.
3. Add the agent to the post-patch checklist.
4. Confirm metrics arrive.

### Maintenance window left open

1. Check for active maintenance windows.
2. Close the expired maintenance window.
3. Review alerts that were suppressed.
4. Confirm alerts fire normally.

### Threshold set too low without grouping

1. Check recent threshold changes.
2. Restore the documented threshold and enable alert grouping.
3. Confirm with the service owner.
4. Confirm alert volume drops.

### Daily ingestion quota reached

1. Check ingestion volume against the daily quota.
2. Reduce debug log volume from the noisy source.
3. Request a quota review with Observability.
4. Confirm logs arrive.

## Validation and escalation

Trigger a test alert and confirm it reaches the right on-call channel, and confirm dashboards show current data.

Escalate to Observability engineering if monitoring is down for many services, because incidents may go unnoticed.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
