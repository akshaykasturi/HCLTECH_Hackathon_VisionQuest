# Suspicious email and phishing reports

## Symptoms and scope

An employee reports a suspicious email, or clicked a link or opened an attachment. The goal is to contain risk quickly and preserve evidence. A ticket about phishing is a normal Security ticket.

This guide covers these known causes:

- Phishing message reported before interaction (typical signal: `reported phish`)
- Credentials submitted to a phishing site (typical signal: `credential harvest`)
- Malicious macro attachment opened (typical signal: `macro execution`)
- Business email compromise attempt (typical signal: `lookalike domain`)
- Phishing campaign bypassed filters (typical signal: `campaign`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need the Security Operations role in the email security console. Never open suspicious links or attachments on a normal workstation. Collect message identifiers, not full content.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Phishing message reported before interaction.** For a reported message with no interaction, search for the same sender and subject across mailboxes.
- **Credentials submitted to a phishing site.** If credentials were entered, check sign-in logs for the account for unfamiliar locations since the click.
- **Malicious macro attachment opened.** If an attachment was opened, check endpoint detection for process activity on the device after the open time.
- **Business email compromise attempt.** For payment change requests, compare the sender domain with the supplier's known domain and check the reply-to address.
- **Phishing campaign bypassed filters.** When many users report a message, measure how many mailboxes received it and whether anyone clicked.

## Resolution steps by cause

### Phishing message reported before interaction

1. Search for the same message across mailboxes.
2. Remove the message from all mailboxes using the email security console.
3. Block the sender domain and URL.
4. Thank the reporter and close with the outcome.

### Credentials submitted to a phishing site

1. Reset the user's password and revoke active sessions.
2. Check sign-in logs for unfamiliar access since the click.
3. Block the phishing URL for all users.
4. Hand the case to the incident response lead if suspicious sign-ins are found.

### Malicious macro attachment opened

1. Isolate the device through endpoint detection.
2. Check process activity after the open time.
3. Remove the message from all mailboxes.
4. Hand the device to Security Operations for analysis.

### Business email compromise attempt

1. Compare the sender and reply-to domains with the known supplier domain.
2. Confirm the request with the supplier using contact details already on file.
3. Block the lookalike domain.
4. Tell finance to hold the payment change until confirmed.

### Phishing campaign bypassed filters

1. Measure how many mailboxes received the message and who clicked.
2. Purge every copy of the campaign message with a single search-and-remove job.
3. Block the sender infrastructure and URLs.
4. Send an awareness notice to staff.

## Validation and escalation

Confirm the message is removed from mailboxes, the sender or URL is blocked, and the reporter knows the outcome.

Escalate to the incident response lead if credentials were entered, malware ran, or many users received the message.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
