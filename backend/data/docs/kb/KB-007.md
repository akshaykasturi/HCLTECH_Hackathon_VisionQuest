# Email delivery delays and failures

## Symptoms and scope

Mail to or from external recipients is delayed, rejected or lands in spam. Causes include sender authentication records, connector settings, reputation and mailbox limits.

This guide covers these known causes:

- Sending service not listed in the domain's SPF record (typical signal: `550 5.7.23 SPF fail`)
- Outbound connector pointing to a smart host that is not responding (typical signal: `451 4.4.0 deferred`)
- Mailbox reached its storage quota (typical signal: `552 5.2.2 mailbox full`)
- Shared sending address listed after a compromised account sent spam (typical signal: `550 5.7.1 listed`)
- New transport rule quarantining outbound attachments (typical signal: `TransportRule quarantine`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need message trace access in the mail admin centre. DNS record changes for mail authentication need an approved change record. Do not forward the content of user messages into tickets.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Sending service not listed in the domain's SPF record.** When external domains reject mail for sender checks, read the authentication results header in a bounced copy and check which sending service failed SPF.
- **Outbound connector pointing to a smart host that is not responding.** If only external mail is delayed, run a message trace and check whether messages are deferred on an outbound connector and to which smart host.
- **Mailbox reached its storage quota.** When one mailbox stops receiving, check its size against the quota and whether archiving is enabled.
- **Shared sending address listed after a compromised account sent spam.** When bounces cite reputation, check outbound spam reports for recent bulk sending by a single account and the block list named in the bounce.
- **New transport rule quarantining outbound attachments.** If outbound messages with attachments are held, check message trace for the transport rule that acted and when the rule was changed.

## Resolution steps by cause

### Sending service not listed in the domain's SPF record

1. Confirm the bounce shows an SPF failure for the sending service.
2. Request an SPF record update that includes the sending service through change control.
3. Wait for the DNS TTL to expire and send a test message.
4. Confirm the test message passes SPF at an external mailbox.

### Outbound connector pointing to a smart host that is not responding

1. Confirm deferred messages and the connector named in the message trace.
2. Check the smart host health with Messaging Operations.
3. Correct the connector to the documented smart host through change control.
4. Confirm queued messages are delivered.

### Mailbox reached its storage quota

1. Confirm the mailbox size is at the quota limit.
2. Enable the online archive and apply the standard retention policy.
3. Help the user move or delete large old items.
4. Confirm new messages arrive.

### Shared sending address listed after a compromised account sent spam

1. Identify any account that sent unusual bulk mail in the outbound spam report.
2. Ask Security Operations to secure the account that sent the spam.
3. Submit a delisting request through the block list's published process.
4. Confirm messages to the affected domains are delivered.

### New transport rule quarantining outbound attachments

1. Identify the transport rule named in the message trace.
2. Confirm with the rule owner whether outbound attachments were meant to be in scope.
3. Adjust the rule scope through change control.
4. Confirm a test attachment reaches an external mailbox.

## Validation and escalation

Run a new message trace for a test message to the affected destination and confirm delivery within the normal time.

Escalate to Messaging Operations engineering if many domains are affected, if the tenant is on a block list, or if mail flow stops completely.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
