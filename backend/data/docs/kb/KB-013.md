# Virtual machine availability problems

## Symptoms and scope

Cloud virtual machines restart repeatedly, fail to start, become unreachable or run slowly. Causes include the guest operating system, disks, quotas and host maintenance.

This guide covers these known causes:

- Faulty kernel or driver update applied during patching (typical signal: `boot diagnostics crash`)
- OS disk filled by application logs (typical signal: `disk 100%`)
- Regional core quota reached (typical signal: `QuotaExceeded`)
- Provider host maintenance restarted the VM (typical signal: `platform maintenance`)
- Burstable VM out of CPU credits (typical signal: `CPU credits 0`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the cloud console, boot diagnostics and VM metrics. Resize, redeploy and disk operations in production need a change record and a recent backup.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Faulty kernel or driver update applied during patching.** When a VM restarts repeatedly after patching, read the boot diagnostics screenshot and serial log for the failing component.
- **OS disk filled by application logs.** If a VM becomes unresponsive, check OS disk usage in metrics before restarting.
- **Regional core quota reached.** When starts fail with quota errors, compare current core usage in the region with the subscription quota.
- **Provider host maintenance restarted the VM.** If a VM restarted without a change, check the activity log and service health notices for planned maintenance.
- **Burstable VM out of CPU credits.** If a small VM slows after sustained load, check its CPU credit balance metric.

## Resolution steps by cause

### Faulty kernel or driver update applied during patching

1. Read the boot diagnostics output for the failing component.
2. Restore the VM from the pre-patch snapshot under the change record.
3. Exclude the faulty update from the next patch run.
4. Confirm the VM stays up and the health check passes.

### OS disk filled by application logs

1. Confirm OS disk usage is at the limit in metrics.
2. Connect through the serial console and move old logs to the attached data disk.
3. Configure log rotation for the application.
4. Confirm the VM responds and disk usage is below the alert threshold.

### Regional core quota reached

1. Compare regional core usage with the quota.
2. Stop or remove unused VMs after confirming with their owners.
3. Submit a quota increase request through the cloud console.
4. Confirm the VM starts.

### Provider host maintenance restarted the VM

1. Confirm the platform maintenance event in the activity log.
2. Place the VMs in an availability set or zone pair.
3. Subscribe the owning team to maintenance notifications.
4. Confirm the application recovered after the restart.

### Burstable VM out of CPU credits

1. Check the CPU credit balance metric.
2. Resize the VM to a non-burstable size under a change record.
3. Review the workload schedule with the owner.
4. Confirm CPU performance is stable.

## Validation and escalation

Confirm the VM is running, the application health check passes and no new restarts appear in the activity log.

Escalate to Cloud Platform engineering if several VMs in one region are affected or if the provider status page reports an incident.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
