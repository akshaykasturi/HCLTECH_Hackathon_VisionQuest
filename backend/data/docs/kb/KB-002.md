# Repeated account lockouts in Active Directory

## Symptoms and scope

A user account keeps locking shortly after it is unlocked, or several accounts lock at the same time. The account is usually locked by repeated failed authentications from a source that still holds an old password.

This guide covers these known causes:

- Mobile mail profile retrying with the old password (typical signal: `Event ID 4740`)
- Persistent mapped drive or scheduled task on a second workstation using old credentials (typical signal: `Event ID 4625 0xC000006A`)
- Application still configured with the service account's previous password (typical signal: `Event ID 4740`)
- Password change not replicated to the branch domain controller (typical signal: `repadmin error 1722`)
- Account lockout threshold lowered by a group policy change (typical signal: `lockout threshold 3`)

## Before you start

You need Service Desk rights to unlock accounts and read access to domain controller security logs. Verify the user's identity before unlocking; never ask the user to tell you their password.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Mobile mail profile retrying with the old password.** Find the lockout event on the domain controller holding the PDC emulator role and read the caller computer name; a mobile mail gateway as the source points to a phone profile with the old password.
- **Persistent mapped drive or scheduled task on a second workstation using old credentials.** When lockouts repeat at fixed times, read the failed logon events for the source workstation and look for scheduled tasks or mapped drives that store credentials.
- **Application still configured with the service account's previous password.** If a service account locks after a password rotation, list every server and application that stores its credentials and check which one still uses the old secret.
- **Password change not replicated to the branch domain controller.** When lockouts are tied to one site, check replication status for the site's domain controller with `repadmin /showrepl` and look for failed inbound replication.
- **Account lockout threshold lowered by a group policy change.** When lockouts suddenly rise for many users, compare the effective account lockout policy with the documented baseline and check recent group policy changes.

## Resolution steps by cause

### Mobile mail profile retrying with the old password

1. Locate the lockout event and identify the calling source.
2. Ask the user to update or remove the mail profile on the mobile device.
3. Unlock the account after identity verification.
4. Confirm the account stays unlocked for one hour.

### Persistent mapped drive or scheduled task on a second workstation using old credentials

1. Identify the workstation named in the failed logon events.
2. Remove saved credentials for mapped drives and scheduled tasks on that workstation.
3. Sign the user out of the idle session on the second workstation.
4. Unlock the account and confirm no failures from that workstation.

### Application still configured with the service account's previous password

1. Confirm the lockout source host from the domain controller event.
2. Update the stored credential on the application server through the secrets vault.
3. Unlock the service account and restart only the affected job.
4. Confirm the next scheduled run completes without failures.

### Password change not replicated to the branch domain controller

1. Check inbound replication status for the branch domain controller.
2. Raise the replication failure with Identity Operations to restore the link.
3. Unlock the account once the domain controller shows the current password.
4. Confirm the user can sign in at the branch site.

### Account lockout threshold lowered by a group policy change

1. Confirm the effective lockout threshold on an affected account.
2. Ask the policy owner to restore the documented lockout threshold through change control.
3. Unlock affected accounts in batches after identity verification.
4. Confirm lockout call volume returns to normal.

## Validation and escalation

After the fix, confirm the account stays unlocked for at least one hour and that no new lockout events appear for the same source.

Escalate to Identity Operations if lockouts come from many unknown sources, if many accounts lock at once, or if the source is outside the corporate network; involve Security Operations for suspected password guessing.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
