# Low disk space on Windows endpoints

## Symptoms and scope

Workstations run out of disk space, causing failed updates, slow performance or applications that cannot save files. The cause is usually a specific folder growing unexpectedly.

This guide covers these known causes:

- Files On-Demand disabled so the sync client downloads entire libraries (typical signal: `disk free 2%`)
- Old update files left in the update cache (typical signal: `0x80070070`)
- Application left in debug logging mode (typical signal: `debug logging enabled`)
- Stale local user profiles on a shared workstation (typical signal: `profile count 63`)
- Entry-level model image includes large hibernation and recovery files (typical signal: `hiberfil 12 GB`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need remote support access through the device management console. Never delete user files without the user's agreement; prefer documented cleanup tools and moving data to supported storage.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Files On-Demand disabled so the sync client downloads entire libraries.** When disk usage grows quickly, find the largest folders with the storage report; a large sync folder points to files being kept locally.
- **Old update files left in the update cache.** If updates fail for space, check the size of the update cache and previous installation folders before looking at user data.
- **Application left in debug logging mode.** When one application folder grows daily, check the application's logging level and log retention settings.
- **Stale local user profiles on a shared workstation.** For shared devices, count local profiles and their last-used dates before removing anything.
- **Entry-level model image includes large hibernation and recovery files.** When a whole model is low on space, compare system file sizes on an affected device with the image baseline.

## Resolution steps by cause

### Files On-Demand disabled so the sync client downloads entire libraries

1. Identify the largest folders using the storage report.
2. Enable Files On-Demand in the sync client settings.
3. Ask the user to set rarely used folders to online-only.
4. Confirm free space is above the documented minimum.

### Old update files left in the update cache

1. Confirm the update error code points to low disk space.
2. Run the built-in disk cleanup for system and update files.
3. Retry the update from the device management console.
4. Confirm the update installs successfully.

### Application left in debug logging mode

1. Identify the log folder that is growing.
2. Set the application logging level back to the documented default.
3. Archive the old logs to the support share if the vendor needs them.
4. Confirm the folder stops growing.

### Stale local user profiles on a shared workstation

1. List local profiles and their last-used dates.
2. Apply the shared-device policy that removes profiles unused for 30 days.
3. Confirm with the site lead before removing any recent profiles.
4. Confirm free space is restored.

### Entry-level model image includes large hibernation and recovery files

1. Compare system file sizes with the image baseline.
2. Apply the documented power profile that reduces the hibernation file.
3. Report the model to Endpoint Engineering for an image review.
4. Confirm free space on the device.

## Validation and escalation

Confirm free space is above the documented minimum and that the original symptom, such as a failed update, no longer occurs.

Escalate to Endpoint Engineering if many devices of the same build fill up at once, which suggests a software defect.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
