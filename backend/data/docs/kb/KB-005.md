# Internal DNS resolution failures

## Symptoms and scope

Internal hostnames do not resolve, resolve to the wrong address, or resolve only from some locations. Causes include stale records, missing records, conditional forwarder problems and client-side caching.

This guide covers these known causes:

- Caching resolver holding a stale record with a long TTL (typical signal: `stale A record`)
- DNS record never created because the request was not completed (typical signal: `NXDOMAIN`)
- Conditional forwarder target unreachable after partner network change (typical signal: `SERVFAIL`)
- VPN profile missing the DNS search suffix list (typical signal: `search suffix missing`)
- Internal zone copy of the public domain missing an updated record (typical signal: `split-horizon mismatch`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the DNS management console. Record changes in production zones require an approved change record. Use read-only lookups such as `Resolve-DnsName` and `nslookup` for diagnosis.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Caching resolver holding a stale record with a long TTL.** When resolvers return an old address, compare the answer from the authoritative server with the caching resolver and note the remaining TTL.
- **DNS record never created because the request was not completed.** If a new name returns NXDOMAIN everywhere, search the zone for the record and check whether the DNS request linked to the deployment was completed.
- **Conditional forwarder target unreachable after partner network change.** When one external domain fails, check the conditional forwarder for that domain and test whether its target servers answer on port 53.
- **VPN profile missing the DNS search suffix list.** If only short names fail for remote users, compare the DNS suffix search list on a VPN client with an office client.
- **Internal zone copy of the public domain missing an updated record.** When a public name behaves differently inside the network, compare the internal zone record with the public DNS answer.

## Resolution steps by cause

### Caching resolver holding a stale record with a long TTL

1. Compare the answer from the authoritative server with the caching resolver.
2. Clear the stale entry from the caching resolver cache.
3. Ask affected users to flush their local DNS cache.
4. Confirm the hostname now resolves to the new address.

### DNS record never created because the request was not completed

1. Confirm the record is missing from the authoritative zone.
2. Find the DNS request for the deployment and its approval.
3. Create the record through the approved change.
4. Confirm the name resolves from two locations.

### Conditional forwarder target unreachable after partner network change

1. Confirm lookups for the partner domain return SERVFAIL.
2. Test reachability of the conditional forwarder targets.
3. Update the forwarder targets with the addresses confirmed by the partner, through change control.
4. Confirm partner names resolve again.

### VPN profile missing the DNS search suffix list

1. Compare the DNS suffix list on a VPN client with an office client.
2. Add the documented search suffixes to the VPN client profile.
3. Ask remote users to reconnect the VPN.
4. Confirm short names resolve over VPN.

### Internal zone copy of the public domain missing an updated record

1. Compare the internal zone record with the public DNS answer.
2. Update the internal zone record to match the published address through change control.
3. Clear the record from the caching resolvers.
4. Confirm the website loads from the office network.

## Validation and escalation

Confirm the name resolves to the expected address from the affected location and from a second location, and that the application opens.

Escalate to Network Operations engineering if several zones are affected, if authoritative servers disagree, or if resolution fails for all users at a site.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
