# PostgreSQL query performance problems

## Symptoms and scope

Queries become slow or time out, reports fail, or the database CPU stays high. Causes include missing indexes, outdated statistics, locks, bloat and resource limits.

This guide covers these known causes:

- Missing index on a new filter column (typical signal: `seq scan on orders`)
- Table statistics outdated after a bulk load (typical signal: `estimated rows mismatch`)
- Long-running idle transaction holding a row lock (typical signal: `idle in transaction`)
- Table bloat because autovacuum cannot keep up (typical signal: `dead tuples high`)
- Replica lagging due to heavy queries on the replica (typical signal: `replication lag 3600s`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read-only access to query statistics and metrics. Index creation and maintenance in production require a change record and must avoid blocking locks during business hours.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Missing index on a new filter column.** When one query slows down, read its plan with `EXPLAIN` on a replica and look for sequential scans on large tables.
- **Table statistics outdated after a bulk load.** If plans change after a bulk load, compare estimated and actual row counts in the plan.
- **Long-running idle transaction holding a row lock.** When sessions wait on locks, find the blocking session with a read-only query and check how long it has been idle in transaction.
- **Table bloat because autovacuum cannot keep up.** If a table grows without more rows, check dead tuple counts and the last autovacuum time.
- **Replica lagging due to heavy queries on the replica.** When reports are stale, check replication lag and long queries running on the replica.

## Resolution steps by cause

### Missing index on a new filter column

1. Read the query plan on a replica.
2. Create the missing index concurrently under a change record.
3. Rerun the report.
4. Confirm the report completes in its normal time.

### Table statistics outdated after a bulk load

1. Compare estimated and actual rows in the query plan.
2. Run ANALYZE on the loaded tables.
3. Add a statistics step to the import job.
4. Confirm query times return to baseline.

### Long-running idle transaction holding a row lock

1. Identify the blocking session and its application.
2. Ask the owning team to end their idle transaction or approve ending the session.
3. Set an idle transaction timeout for the application role through change control.
4. Confirm waiting sessions clear.

### Table bloat because autovacuum cannot keep up

1. Check dead tuples and last autovacuum time for the table.
2. Tune autovacuum settings for the table through change control.
3. Schedule maintenance during a low-traffic window.
4. Confirm dead tuples and query times drop.

### Replica lagging due to heavy queries on the replica

1. Check replication lag and long-running replica queries.
2. Ask the report owner to reschedule the heavy query.
3. Set a statement timeout for reporting users on the replica through change control.
4. Confirm replication lag returns to normal.

## Validation and escalation

Confirm the affected query or report completes within its normal time and that CPU and lock metrics are back to baseline.

Escalate to Database Operations engineering for sustained high load on the primary, replication lag, or blocking that affects many applications.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
