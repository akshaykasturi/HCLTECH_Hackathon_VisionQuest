# Object storage access errors

## Symptoms and scope

Applications or users get access denied, missing object or throttling errors from object storage. Causes include identity permissions, bucket policies, keys and network restrictions.

This guide covers these known causes:

- Workload identity missing the storage write role (typical signal: `403 AccessDenied`)
- Integration still using the rotated access key (typical signal: `SignatureDoesNotMatch`)
- Storage firewall does not allow the new subnet (typical signal: `network rule denied`)
- Request rate above the partition limit on a single prefix (typical signal: `503 SlowDown`)
- Lifecycle rule expiring objects in the wrong prefix (typical signal: `lifecycle expiration`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the cloud console and storage access logs. Permission changes go through infrastructure-as-code and change control. Never paste access keys or connection strings into tickets.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Workload identity missing the storage write role.** When a new deployment gets access denied, read the storage access log for the caller identity and compare with its assigned roles.
- **Integration still using the rotated access key.** If failures started at a key rotation, check which credential the integration uses and whether it reads from the secrets vault.
- **Storage firewall does not allow the new subnet.** When some networks time out, compare the caller subnet with the storage account network rules.
- **Request rate above the partition limit on a single prefix.** If errors appear only under load, check the request rate per prefix in storage metrics.
- **Lifecycle rule expiring objects in the wrong prefix.** When old objects vanish, check the bucket lifecycle rules and which prefixes they apply to.

## Resolution steps by cause

### Workload identity missing the storage write role

1. Identify the caller identity in the storage access log.
2. Add the documented storage role to the workload identity through infrastructure-as-code.
3. Redeploy or restart the workload so it picks up the new token.
4. Confirm writes succeed in the storage log.

### Integration still using the rotated access key

1. Confirm the failure started at the key rotation time.
2. Update the integration to read the current key from the secrets vault.
3. Rerun the failed batch job.
4. Confirm the job reads from the bucket.

### Storage firewall does not allow the new subnet

1. Compare the caller subnet with the storage network rules.
2. Add the subnet to the storage network rules through infrastructure-as-code.
3. Retry the request from the VM.
4. Confirm the request completes.

### Request rate above the partition limit on a single prefix

1. Confirm throttling responses in storage metrics during the peak.
2. Enable retry with exponential backoff in the client configuration.
3. Ask the application team to spread objects across more prefixes.
4. Confirm throttling errors drop.

### Lifecycle rule expiring objects in the wrong prefix

1. Review the bucket lifecycle rules and their prefixes.
2. Ask the data owner to confirm the intended retention.
3. Correct the lifecycle rule scope through infrastructure-as-code.
4. Restore objects from versioning where available and confirm with the owner.

## Validation and escalation

Confirm the application completes its read or write and that storage logs show success for the caller.

Escalate to Cloud Platform engineering if data appears exposed publicly or if many applications fail at once.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
