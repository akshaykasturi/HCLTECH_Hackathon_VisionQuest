# PostgreSQL connection failures

## Symptoms and scope

Applications cannot connect to a PostgreSQL database, or connections fail intermittently. Causes include connection limits, credentials, TLS settings, network rules and failover.

This guide covers these known causes:

- Connection limit reached because the application does not use a pool (typical signal: `SQLSTATE 53300`)
- Application role password rotated but not updated in the application (typical signal: `28P01`)
- Server now enforces TLS and the client connects without it (typical signal: `no pg_hba.conf entry ... no encryption`)
- Application caching the old primary address after failover (typical signal: `read-only transaction`)
- Database network rules do not allow the new subnet (typical signal: `connection timed out`)

## Before you start

You need read-only access to database metrics and logs. Do not run write statements or change server parameters in production without a change record. Never share connection strings in tickets.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Connection limit reached because the application does not use a pool.** When new connections are refused, count active and idle sessions per application with a read-only query on `pg_stat_activity`.
- **Application role password rotated but not updated in the application.** If authentication fails for one role, check when the role credential was rotated and where the application reads it.
- **Server now enforces TLS and the client connects without it.** When connections fail after a server change, read the rejection message to see whether encryption is required.
- **Application caching the old primary address after failover.** If writes fail after a failover, check which host the application resolves and whether it uses the cluster endpoint.
- **Database network rules do not allow the new subnet.** When only new hosts time out, compare their subnet with the database firewall rules.

## Resolution steps by cause

### Connection limit reached because the application does not use a pool

1. Count sessions per application in pg_stat_activity.
2. Route the application through the documented connection pooler.
3. Ask the application team to close idle connections.
4. Confirm connections succeed during peak.

### Application role password rotated but not updated in the application

1. Confirm the authentication failure for the role in the database log.
2. Update the application to read the current credential from the secrets vault.
3. Restart the application.
4. Confirm the application connects.

### Server now enforces TLS and the client connects without it

1. Confirm the rejection mentions missing encryption.
2. Set the client connection to require TLS using the documented settings.
3. Install the database CA certificate on the client host.
4. Confirm the client connects over TLS.

### Application caching the old primary address after failover

1. Confirm which host the application is connected to.
2. Point the application to the cluster writer endpoint.
3. Restart the application connection pool.
4. Confirm writes succeed.

### Database network rules do not allow the new subnet

1. Compare the new hosts' subnet with the database firewall rules.
2. Add the subnet to the firewall rules through change control.
3. Retry the connection from a new host.
4. Confirm connections succeed.

## Validation and escalation

Confirm the application connects, its health check passes and the database log shows no new connection errors.

Escalate to Database Operations engineering if the primary is unavailable, if failover did not complete, or if data loss is suspected.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
