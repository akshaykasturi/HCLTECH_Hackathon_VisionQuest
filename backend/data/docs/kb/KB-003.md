# Access provisioning failures and delays

## Symptoms and scope

A user does not receive the access they requested or were entitled to, or keeps access they should have lost. These issues come from the joiner, mover and leaver workflows, approvals and the connectors that push changes to target applications.

This guide covers these known causes:

- Employee record missing from the HR feed because the start date was not entered (typical signal: `HRFEED-MISSING-ID`)
- Provisioning connector failing to authenticate to the target application (typical signal: `connector 401 Unauthorized`)
- Approval routed to an approver who has left the organisation (typical signal: `approval pending 7 days`)
- Mover workflow did not trigger because the department change was back-dated (typical signal: `mover event not raised`)
- Termination workflow failed at the disable step (typical signal: `WF-TERM-FAIL`)

Synthetic guidance written for development and evaluation; it is not the approved procedure of any real organisation.

## Before you start

You need read access to the access governance console and the request history. Never grant access manually outside the request workflow; every grant needs a recorded approval.

Record the ticket ID, the affected users or systems, the start time and any recent changes before you act. Do not assume a cause from symptoms alone: match the observed signal to a cause below.

## Diagnostic checks

- **Employee record missing from the HR feed because the start date was not entered.** If a joiner has no account, search the latest HR feed import for the employee number and check the start date and status fields.
- **Provisioning connector failing to authenticate to the target application.** When approved requests stall for one application, open the connector status page and read the last error; repeated authentication errors mean the connector credential expired.
- **Approval routed to an approver who has left the organisation.** For requests pending longer than the approval target, check the approver's account status and the resource owner recorded in the catalogue.
- **Mover workflow did not trigger because the department change was back-dated.** When a transferred user keeps old access, compare the department change date in the HR record with the mover workflow history.
- **Termination workflow failed at the disable step.** If a leaver account is still enabled, open the termination workflow history and find the step that failed and its error.

## Resolution steps by cause

### Employee record missing from the HR feed because the start date was not entered

1. Confirm the employee number is absent from the latest HR feed import.
2. Ask HR operations to complete the start date in the HR record.
3. Run the next scheduled joiner sync rather than creating the account by hand.
4. Confirm the account and birthright access exist after the sync.

### Provisioning connector failing to authenticate to the target application

1. Confirm the connector shows authentication errors for the target application.
2. Ask IAM Engineering to renew the connector credential through the secrets vault.
3. Retry the stalled provisioning tasks from the governance console.
4. Confirm the user can see the requested role.

### Approval routed to an approver who has left the organisation

1. Check whether the assigned approver account is disabled.
2. Ask the resource owner's manager to name a new approver in the catalogue.
3. Reassign the pending request to the new approver.
4. Confirm the request completes after approval.

### Mover workflow did not trigger because the department change was back-dated

1. Confirm no mover workflow ran for the department change.
2. Ask the previous manager to confirm which roles should be removed.
3. Submit removal requests for the previous roles through the governance console.
4. Confirm the previous team access is gone.

### Termination workflow failed at the disable step

1. Confirm the termination workflow failed at the disable step.
2. Disable the account through the governance console and revoke active sessions.
3. Notify Security Operations so they can review recent account activity.
4. Confirm the account is disabled and the workflow is marked complete.

## Validation and escalation

Confirm the target application shows the expected entitlement, and that the request history shows the request completed with an approval.

Escalate to IAM Engineering for connector failures affecting several applications; escalate to Security Operations if a leaver account remains active.

Also escalate when the observed facts match none of the causes above, when a step fails, or when the impact grows while you work. Record each step taken and its result in the ticket.
